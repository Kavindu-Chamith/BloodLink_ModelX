# Postman backend workflow checks

The collection contains 127 ordered requests covering all 82 declared backend routes. It is generated by `build-collection.cjs` and runs with the installed Postman CLI. No Postman login is required for this local collection. The runner passes `--no-report-events`; it does not publish the collection or run results. See [Postman's collection command documentation](https://learning.postman.com/docs/postman-cli/postman-cli-collections/).

## Run automatically

From `backend`:

```sh
npm run test:postman
```

Requirements: installed backend dependencies, Postman CLI on PATH, and PostgreSQL credentials with CREATEDB permission. Set `POSTMAN_CLI` to the executable's absolute path if necessary. The runner uses `TEST_DATABASE_URL`, otherwise `MIGRATION_DATABASE_URL`, otherwise `DATABASE_URL` from `backend/.env`. Nonlocal connections require explicit `TEST_DATABASE_URL`.

The runner creates a randomly named disposable database, applies all migrations, creates one synthetic administrator, and starts the API on a temporary loopback port. The remaining accounts and workflow records are created through HTTP. It runs Postman and removes the database in `finally`. It never runs collection mutations against the configured application's tables.

The sanitized [last-run.json](last-run.json) records assertion counts, CLI exit status, route coverage and observed response statuses. Generated passwords, temporary environments and the full CLI log remain in the ignored `.qa-private/postman/` directory. No real account credentials are included in the collection.

## Run in the Postman application

```sh
npm run test:postman:serve
```

1. Keep this process running and import `BloodLink.postman_collection.json`.
2. Import and select the temporary environment at the path printed by the command.
3. Set Postman's working directory to `backend/postman` so `fixtures/verification.pdf` can be uploaded.
4. Use Collection Runner to run all folders once, in order, with one iteration. Keep the default request methods, bodies and assertions.
5. Press Ctrl+C in the harness terminal afterward to remove the disposable database. Start a fresh harness for another run; registration proofs and PDF links are intentionally single use.

The collection's prerequisite script requires the disposable loopback environment. It is not intended to run against a shared or production installation.

## What the checks verify

- Public health and institution discovery; authentication and role rejection.
- Actual email OTP creation, proof consumption, registration, profile updates and availability.
- Multipart document upload, private downloads, rejected review, resubmission and approval.
- Hospital and bank onboarding, staff review, primary account assignment, temporary password replacement, user and institution suspension/reactivation.
- Institution stock groups, derived status and stale-update rejection; primary-account teammate administration.
- Request creation, approval/rejection/cancellation, donor matching, response aliases, mission cancellation, coordinator cooldown, donation confirmation and idempotency.
- Donation history and one-use PDF links; private health messages, notification read state and device endpoint validation.
- Password recovery through the persisted reset queue, session revocation, refresh rotation and logout.

Expected 400/401/403/404/409/429 responses are successful negative tests, not backend failures. The final run also requires that every inventoried route was reached and no unexpected server errors occurred.

## Boundaries of the result

- Email delivery is captured by a protected, loopback-only test inbox in the harness. Production API routes are unchanged. SMTP inbox delivery is not verified.
- FCM is disabled. `POST /api/notifications/devices` is expected to return 503. The collection verifies its unconfigured response, not successful native push registration or physical-device delivery.
- The harness resets only the general IP counter between requests because the collection exceeds its 100-request window. Route-specific limiters remain active; the collection checks shared registration throttling and coordinator cooldown.
- This is a sequential workflow run, not exhaustive input, concurrency, load or production deployment testing. Run `npm test` for the additional security, concurrency, queue recovery and migration checks.
- Command output may mention that credentials are required to publish results. Publishing is not requested; a local passing run exits with code 0.
